# Purchase Service

`purchase-service` - это веб-сервис для управления закупками: пользователь оформляет заказ на товар, а администратор ведет его по статусам до получения.

## Цель

Централизовать процесс закупок в одном интерфейсе:

- принять заявку от пользователя;
- сохранить данные о товаре;
- дать пользователю возможность отслеживать заказ;
- дать администратору очередь заказов, управление статусами, пользователями и архивом.

Идея сервиса отражена на главной странице: "Одна страница - все закупки", регистрация, оформление заказа и отслеживание этапов: [views/welcome.hbs](../views/welcome.hbs).

## Задачи, которые решает проект

- Прием заявок на покупку товаров: название, количество, стоимость, ссылка, желаемая дата доставки.
- Разделение ролей: обычный пользователь видит свои заказы, администратор управляет всеми заказами и пользователями.
- Отслеживание жизненного цикла заказа: `На рассмотрении`, `Закупаем`, `Доставляем`, `Ожидает получения`, `Получен`.
- Управление пользователями: добавление, редактирование, удаление, просмотр количества заказов.
- Управление заказами: просмотр активных, фильтрация по статусу, изменение данных, обновление статуса.
- Архивация завершенных заказов со статусом `Получен`.
- Учет суммарной стоимости заказов в админской панели.
- Поиск и пагинация для списков пользователей и заказов.

## Ключевые механики

### Регистрация и вход

Пользователь регистрируется, логин проверяется на уникальность. После входа пользователь перенаправляется либо в `/myorders`, либо в `/manageorders` в зависимости от значения `is_admin`.

Код: [vendor/db.js](../vendor/db.js).

### Ролевая защита маршрутов

Доступ к разделам ограничивают middleware-функции:

- `ensureAuthenticated`;
- `ensureAdmin`;
- `ensureUser`.

Код: [buy.js](../buy.js).

### Личный кабинет пользователя

Пользователь может:

- добавлять заказ;
- просматривать свои заказы;
- искать заказ по названию товара;
- редактировать заказ.

Основные маршруты:

- `GET /myorders`;
- `POST /myorders`;
- `GET /myorders/addorder`;
- `POST /myorders/addorder`;
- `GET /myorders/editorder/:id`;
- `POST /myorders/editorder/:id`.

### Создание заказа

Новый заказ автоматически получает статус `На рассмотрении`.

Данные заказа:

- название товара;
- количество;
- стоимость;
- ссылка на товар;
- дата оформления;
- желаемая дата доставки;
- автор заказа;
- статус.

### Админская очередь заказов

Администратор видит активные заказы, фильтрует их по статусу, меняет данные заказа и обновляет статус.

Основные маршруты:

- `GET /manageorders`;
- `GET /manageorders/editorderadmin/:id`;
- `POST /manageorders/editorderadmin/:id`;
- `POST /updateOrderStatus/:id`.

### Архив

Заказы со статусом `Получен` выводятся отдельно в архиве.

Маршрут: `GET /ordersarchive`.

### База данных

Основные сущности:

- `users` - пользователи и роли;
- `orders` - заявки на закупку.

Заказ связан с пользователем через поле `orders.author_id`.

SQL-структура: [sql_database/purchase_service(3).sql](../sql_database/purchase_service%283%29.sql).

## Кратко

Это не магазин и не платежная система, а внутренняя система заявок на закупку. Пользователь просит купить товар, администратор обрабатывает заявку, меняет статусы и ведет историю завершенных заказов.

Технически это Node.js/Express + Handlebars + MySQL-приложение: [package.json](../package.json).
